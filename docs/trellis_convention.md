# Trellis 慣例（凍結）

> **這份文件是 C2 能否通過的槓桿點。** L2、GPU-L2、RTL 三方都從本文件實作。
> 任何一方的狀態標號、survivor 極性或 tie-break 與本文件不符，C2 就會噴出大量 mismatch，
> 而且症狀看起來像「隨機的位元錯誤」，極難 debug。
>
> 本文件的每一條都由 `scripts/verify_trellis.py` 驗證，不是抄來的。

## 1. 碼

| 項目 | 值 |
|---|---|
| 約束長度 K | 7 |
| 記憶元 m = K−1 | 6 |
| 狀態數 | 64 |
| 生成多項式 | (133, 171)₈ |
| 碼率 | 1/2 |
| d_free | **10**（由 `Trellis.free_distance()` 廣度優先搜尋驗證） |

## 2. 狀態與次態

```
s' = ((s << 1) | u) & 0x3F
```

**新輸入從最低位進入。** 於是：

- `s` 的 bit k = `u_{t-1-k}`（bit 0 = 最近一次輸入，bit 5 = 最舊的一次）
- **進入狀態 `s` 的輸入位元 = `s & 1`**
- `s` 的兩個前驅 = `s >> 1` 與 `(s >> 1) + 32`

### Butterfly

**butterfly `j ∈ [0,31]` 吃 `PM[j]` 與 `PM[j+32]`，吐 `PM[2j]` 與 `PM[2j+1]`。**

推導：由 `s = j`（bit 5 = 0）出發 → `s' = 2j + u`；由 `s = j+32`（bit 5 = 1）出發 →
`s' = (2j + 64 + u) & 63 = 2j + u`。兩者落在同一對次態上。

## 3. Survivor 的極性（凍結）

```
survivor[s'] = 0  =>  前驅是  s' >> 1
survivor[s'] = 1  =>  前驅是 (s' >> 1) + 32
```

## 4. Tie-break（凍結）

**`PM_a == PM_b` 時選 survivor bit 0**（即較低編號的前驅）。

這對應 `np.argmin` 的語意（回傳第一個最小值）。三方都必須採同一規則：

- **L2（numpy）**：`np.argmin` 自然符合。
- **GPU-L2（torch）**：`torch.minimum` 是逐元素運算、**不回傳索引**，survivor bit 得自己算。
  必須寫 `sel_a = (sum_a <= sum_b)`——用 `<=` 而不是 `<`。
- **RTL**：`diff = sum_b − sum_a; sel_a = ~diff[W-1]`。
  減法方向刻意是 b−a，這樣 `diff == 0`（平手）時 `sel_a = 1`，**不需要額外的等於比較器**。

**Q=3 時整數平手很常見**（軟值只有 8 階）。三方選錯方向不會報任何錯，只會讓 C2 在
RTL 上線後噴 mismatch，或讓 GPU 掃描的 BER 與 CPU golden 對不起來。M0 的 GPU 煙霧測試
刻意斷言「平手樣本數 > 0」，就是為了確保這條語意真的被測到。

## 5. 生成多項式的位元順序

多項式以八進位給定，**最高位對應當前輸入 u_t，最低位對應最舊的 u_{t-6}**：

```
g0 = 133₈ = 0b1011011
     bit 6 -> u_t     (1)      bit 2 -> u_{t-4}  (0)
     bit 5 -> u_{t-1} (0)      bit 1 -> u_{t-5}  (1)
     bit 4 -> u_{t-2} (1)      bit 0 -> u_{t-6}  (1)
     bit 3 -> u_{t-3} (1)

c0 = u_t ^ u_{t-2} ^ u_{t-3} ^ u_{t-5} ^ u_{t-6}
c1 = u_t ^ u_{t-1} ^ u_{t-2} ^ u_{t-3} ^ u_{t-6}      (g1 = 171₈ = 0b1111001)
```

碼字 `c` 是 2 位元整數 `(c0 << 1) | c1`。

## 6. 兩條互補性（**已驗證**，butterfly 架構的立足點）

這兩條**不是對所有卷積碼都成立**，所以 `Trellis.__init__` 每次都當場驗證，不是假設。

| 性質 | 敘述 | 成立條件 | (133,171) |
|---|---|---|---|
| **P1** | `c(s, u=1) = ~c(s, u=0)` | 每個多項式的 **bit m（MSB）= 1**（有當前輸入的抽頭） | 成立 |
| **P2** | `c(p+32, u) = ~c(p, u)` | 每個多項式的 **bit 0（LSB）= 1**，即**每個八進位多項式都是奇數** | 成立（133₈、171₈ 皆為奇數） |

> **注意**：P2 的條件是 **LSB**，不是 MSB。（執行計畫書 §3.1 誤植為「MSB tap 都是 1」——
> 那是 P1 的條件。兩條性質都成立，但理由不同。此處以 `verify_trellis.py` 的實測為準。）

### 後果：每個 butterfly 只需要一個 branch metric 輸入

令 `X = c(j, 0)`。由 P1 與 P2：

```
c(j,    0) = X          c(j,    1) = ~X
c(j+32, 0) = ~X         c(j+32, 1) = X
```

且 `bm[c] + bm[c^3] = λ_max`（見 `docs/wordlength_bound.md`）。所以：

```
PM[2j]   = min( PM[j]    + bm[X],            PM[j+32] + (λ_max − bm[X]) )
PM[2j+1] = min( PM[j]    + (λ_max − bm[X]),  PM[j+32] + bm[X]           )
```

**一個 butterfly 只需要一個 `bm[X]`。** 這是 radix-2 ACS 的標準結構。

## 8. RTL 不得匯入 L2 的 trellis 表

RTL 必須從八進位多項式在 elaboration 時**自行推導**這張表。

理由：若兩邊共用同一份表，表本身若有 bug 就變成 **common-mode 錯誤**，C2 對它完全盲目
（兩邊會「錯同一個錯」）。這正是規格書 §2.1 說的最重要的反模式。

RTL 端加一個 KAT，把 elaborate 出來的表 dump 出來與本文件的 §7 手算表 diff。

## 9. 與既有通訊模擬器的關係（oracle）

既有模擬器的 K=3 用的是**相反**的狀態慣例（新輸入進最高位，`ns = (u<<1)|d1`），
所以兩邊的**狀態編號對不起來**。這不影響它當 oracle：

- **碼字序列是一樣的**（`out1 = u^d1^d2` 就是 g=7 的展開，`out2 = u^d2` 就是 g=5 的展開）。
- 已驗證：把 K=3 (7,5) 灌進本專案的泛用 trellis，編碼器輸出與 `commsim.coding.conv_encode`
  在 50 frames × 200 info bits 上**逐位元組相等**。
- 因此可以拿它經過 mutation testing（90.4%）且驗證過「與暴力 ML 枚舉相等」的解碼器，
  來驗證本專案的解碼引擎。
